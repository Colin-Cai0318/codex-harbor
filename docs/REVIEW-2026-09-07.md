# Original-conversation recovery and writer ownership

## Findings

- The long-lived Harbor App Server retained threads after worker completion. A
  live second-client resume reproduced `already has an active writer`. Closing
  the writer process allowed immediate resume of the exact same thread.
- The reported Linux lab task was created without `origin_thread_id`,
  `conversation_mode`, or a parent session. Its new root thread was therefore
  expected under the previous API contract. Read-only history inspection showed
  an initial `usageLimitExceeded` turn and a later completed turn. Historical
  conversations were not rewritten or combined.
- An empty `thread/start` is not necessarily persisted before the first turn.
  Closing a creation-only client reproduced `no rollout found`. New tasks now
  create their thread inside the worker that executes its first turn.
- Long history responses can exceed asyncio's default 64 KiB line limit. The
  JSON-RPC stream now accepts larger lines; recovery watches query only the latest
  turn using the locally generated `thread/turns/list` schema. Resume excludes
  returned history while retaining the server's persisted context.

## Changes and invariants

- Each daemon worker owns a separate App Server process and closes it on success,
  failure, cancellation, or quota wait. The control connection remains available
  for read-only metadata and quota operations. Cancellation routes to the owning
  worker client.
- Explicit existing-thread tasks bind the root thread atomically with task
  creation. They never fall back to a fork or a new thread. Writer contention
  waits 60 seconds and does not count as an execution failure. Admission also
  serializes tasks sharing the same thread even with different exclusive groups.
- Recovery watches are SQLite-backed and idempotent per active original thread.
  At the configured primary quota threshold (default 95%), a task is atomically
  created in `WAIT_QUOTA`. It remains armed until a real quota-failure turn is
  observed. Fresh quota telemetry and its reset boundary gate release. Failed
  quota refreshes cannot release tasks using stale cached availability.
- A normally completed original turn cancels its pending recovery; explicit
  watch cancellation is rechecked under the database write lock. A user-completed
  continuation before the first Harbor attempt also cancels its pending watch.
- The Chinese skill and standalone loopback-only helper register protection
  without model inference. Thus depleted primary quota cannot itself prevent
  task creation. The opt-in reserve setting uses `gpt-reserve / xhigh` for a single
  same-thread checkpoint when quota is exhausted and no task exists, preserving
  the main model for resumed work. Ordinary Luna is not the reserve entrypoint.

## Validation

- Local suite: **106 passed**. Scoped Ruff checks, Python compilation, and skill
  validation passed. The installed helper completed an arm/list/cancel round trip
  against the restarted daemon; the reserve setting was enabled and read back.

- Automated regression includes threshold/failure/reset transitions, idempotence,
  restart persistence, cancellation races, non-Project conversations, strict
  identity preservation, writer contention, worker-client cleanup on quota wait,
  and a real subprocess JSON-RPC response larger than 64 KiB.
- `tools/same_thread_e2e.py --execute`: three real `gpt-5.6-luna` turns using
  `low -> xhigh -> low`, one constant Thread ID, random-token history recall,
  restoration of the original effort, and immediate independent-client resume
  after worker exit. The control client's loaded-thread list remained empty.
- The end-to-end quota failure/reset is deliberately simulated in an isolated
  Harbor database. No real account quota was exhausted or awaited. Live evidence
  remains in ignored `.harbor/same-thread-*/evidence.json`.
- Skill frontmatter validation, helper invocation, Python compilation, and scoped
  Ruff checks are part of the release checks.

## Operational limits

The desktop may still hold the original writer lock; Harbor waits for release
instead of forcibly taking it or forking. The lock is expected while a Harbor
worker is executing. Reserve availability is verified against the separate `gpt-reserve` bucket.
The installed desktop assets and hidden model registry confirm the reserve model
and xhigh effort; reserve transport is covered with mocks, not a depleted live
primary allowance. The three real turns described above used ordinary Luna. A skill is not a background process: monitoring
requires the daemon. These checks do not qualify reboot recovery, multiple daemon
deployment, or a real five-hour reset cycle.

Protocol reference: [official App Server documentation](https://learn.chatgpt.com/docs/app-server).
Local protocol verification used `codex-cli 0.153.4` and
`codex app-server generate-json-schema --experimental`.
